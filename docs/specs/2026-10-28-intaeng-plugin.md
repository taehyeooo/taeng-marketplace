# intaeng 플러그인 설계 — /지식베이스·/기획·/디자인·작업 흐름

2026-10-28. 사용자와 대화로 정한 범위를 옮긴다. 이슈 #2.

## 왜
- 새 프로젝트를 intaengligence(비공개, 지식베이스가 있는 레포) 밖의 다른 레포에서 하기로 했다. 그 레포에서도 같은 방식으로 일하고 싶다: "/지식베이스 라고 하면 지식 베이스가 깔리고 … /기획 이렇게 하면 지식베이스에 있는 기획단이 돌아가는"(사용자, 2026-10-28).
- intaengligence는 계속 **나 없이도 개발이 돌아가는 본사**(결정·기록이 쌓이고 방식을 고치는 곳)로 두고, 다른 레포에서도 쓸 **방법**만 이 마켓플레이스에 플러그인으로 포장한다(intaengligence ADR 0012 v3).
- 설치는 한 번에: `/plugin install intaeng@taeng-marketplace`(사용자 선택, 2026-10-28).

## 공통 원칙
- **방법만 넣고 기록은 넣지 않는다.** 이 레포는 공개다. intaengligence의 결정 이유(사용자 말 그대로), 작업 기록, 조사, 다른 프로젝트, 이 레포 전용 결정(폴더 구조·Gradle·스타터)은 넣지 않는다. 원칙 ADR은 일반 문장으로 새로 쓴다.
- **깔린 파일은 그 레포 소유다.** `/지식베이스`가 깐 뒤로 그 레포의 CLAUDE.md·문서는 따로 바뀐다. 스킬·명령은 플러그인 업데이트로 따라온다.
- 이미 있는 파일은 덮어쓰지 않는다(startflow와 같게 `*.intaeng.*`로 옆에).
- 비용 0원: 외부 유료 API를 부르지 않는다.
- 혼자 하는 개발용이다. 사람 팀을 전제하지 않고, 에이전트 여럿을 띄우는 단계도 기본으로 두지 않는다(토큰·시간).

## 명령 (설치 뒤)

| 명령 | 하는 일 | 원본(intaengligence) |
|---|---|---|
| `/지식베이스` | 새 레포에 일하는 방식의 뼈대를 깐다 | CLAUDE.md 규칙, `knowledge-base/` 구조, `docs/templates/`, 검사 스크립트·훅·CI, `.claude/rules/` |
| `/기획` | 아이디어 → PRD → 기능 트리 → 기능별 상세 → 데이터 모델 → 자체 점검 → 기능명세서, 단계마다 멈추고 애매한 정책은 객관식으로 묻는다 | 사용자의 기능명세서 스킬(2026-10-28), `start-task` 4·5 |
| `/디자인` | 디자인 4단계를 돈다 | ADR 0029, `design-review`·`design-iterate`·`ux-writing-ko`, 디자인 가이드 일반 부분 |
| `/시작` `/마무리` `/이어하기` `/머지` `/맡기기` `/스펙점검` | 작업 흐름 | `start-task`·`wrap-up`·`resume`·`merge-train`·`delegate-pr`·`spec-check` |

명령 이름은 한글로 시도한다. 플러그인 스킬이 `/intaeng:지식베이스`처럼 앞에 이름이 붙어 보이는지, 한글 이름이 되는지는 PR 1에서 확인한다(R-1). 안 되면 영어(`/kb`·`/plan`·`/design`)로 하고 사용자에게 알린다.

## 요구사항

### 공통
- **R-1** 한글 명령 이름이 플러그인 스킬로 동작하는지 실제로 설치해 확인하고, 결과(이름 앞 `intaeng:` 붙는지 포함)를 README에 적는다.
- **R-2** `marketplace.json`에 `intaeng`, 플러그인 README(설치·명령 표·무엇이 깔리나·무엇이 안 들어가나).
- **R-3** 누출 검사: 플러그인 파일에 intaengligence 전용 내용이 없는지 테스트로 막는다(금지어 목록 — 레포 이름·내 서비스 이름·사용자 인용 표시·내 PC 경로 등).

### /지식베이스
- **R-4** 깔리는 구조: `CLAUDE.md`(규칙만 — 서비스 소개·스택은 묻고 채운다), `knowledge-base/`(index·decisions/README·log·now, troubleshooting·concepts·runbooks의 README), `docs/specs`·`docs/plans` 자리.
- **R-5** 양식 6개: spec·plan·ADR·인터뷰·트러블슈팅·리허설.
- **R-6** 기본 원칙 ADR 15개를 일반 문장으로: 기록 위치, 비용 0원, 샘플로 먼저 검증, 문서 버전, MCP는 쓰는 것만, 코드 스타일, 코드가 기준, 커밋·문서·기록 검사, 운영 정보 기본 꺼짐, 관리자 조치 확인, 경로별 규칙, 요구사항 ID, now.md 인계, 자율 모드.
- **R-7** 검사 도구: 문서·컨텍스트·기록 검사, 커밋 메시지 훅, 워크트리 정리, GitHub Actions(문서·기록·커밋 잡만 — 무거운 빌드는 그 레포가 더한다).
- **R-8** `.claude/rules/` 문서 규칙·상황별 스킬 표.
- **R-9** 먼저 무엇이 생기는지 보여 주고(dry-run) 승인 뒤 깐다. 깐 뒤 검사 도구가 그 레포에서 통과한다.

### /기획
- **R-10** 사용자가 준 기능명세서 과정을 그대로 따른다: 0 아이디어 받기 → 1 PRD 초안 → 2 기능 트리(번호, Mermaid mindmap, 필수 기반 기능은 따로 표시해 포함 여부를 묻기) → 3 기능별 상세(설명·권한·비즈니스 규칙·데이터·화면·예외) → 4 데이터 모델(엔티티·관계·제약, Mermaid erDiagram, 행 단위 권한) → 5 자체 점검 체크리스트 → 6 "확정"이면 최종 문서. 단계마다 멈추고 확인받는다.
- **R-11** 애매한 정책은 임의로 정하지 않고 객관식으로 묻는다(질문당 선택지 3~4개, 추천안에 "(추천)", 직접 입력 허용, 한 번에 최대 4개). 답은 "결정 사항"에 쌓는다. 아이디어 밖 기능은 "추가 제안"으로만.
- **R-12** 최종 문서는 이 레포 양식으로 저장한다: `docs/specs/YYYY-MM-DD-<이름>.md`(frontmatter `title`·`version`·`status`), 세부 기능마다 요구사항 ID(`R-1`…) — plan·테스트로 이어지고 문서 검사가 돈다. 여러 기능에 걸친 큰 정책은 ADR로도 남길지 묻는다. 사람 손이 필요한 일(키·DB·가입)은 0단계에서 한 번에 묻는다.

### /디자인
- **R-13** 디자인 4단계: 구조 시안 3개 → 세부 시안(느낌·UX 디테일) → 적용 → 의견으로 고도화. 시안은 실제 앱 안 변형으로(아티팩트 여러 장 금지 — 토큰).
- **R-14** 시안은 서로 다른 방향 3개를 만들어 사용자가 고른다(에이전트를 여럿 띄울지는 `/디자인` spec 때 사용자와 정한다).
- **R-15** `design-review`·`design-iterate`·`ux-writing-ko`를 함께 넣는다. 화면 PR 본문에 스킬 적용 표.

### 작업 흐름
- **R-16** 6개 스킬을 일반화: intaengligence 경로(`services/`·`packages/`·특정 ADR 번호)를 빼고 R-4 구조 기준으로.

## 순서 (PR)
1. 플러그인 틀 + 한글 명령 확인(R-1·R-2·R-3) + `/지식베이스`(R-4~R-9)
2. 작업 흐름(R-16)
3. `/기획`(R-10~R-12)
4. `/디자인`(R-13~R-15)
5. 첫 새 프로젝트에서 실제로 써 보고 고친다(리허설처럼).

## 범위 밖
- intaengligence의 지식(결정·기록·조사·프로젝트) 내용.
- `packages/` 스타터(로그인·결제), `packages/design`(토큰·부품·화면 검수 도구) — 새 프로젝트에서 필요해지면 따로.
- 기존 플러그인(startflow·uiflow·devflow) 고치기 — 겹침 정리는 intaeng이 자리 잡은 뒤.

## 열린 질문
- **원본은 어디인가**: 같은 스킬이 intaengligence `.claude/skills/`와 이 플러그인에 둘 다 있으면 따로 낡는다. 제안: 일반 스킬은 이 플러그인이 원본, intaengligence도 플러그인을 설치해 쓰고 레포 전용 스킬만 남긴다 — 사용자 확인 필요.
- startflow `kickoff`(Trova가 쓰는 `docs/adr`·`docs/experience-notes.md` 구조)와 `/지식베이스`(`knowledge-base/` 구조)가 겹친다. 당분간 둘 다 두고, intaeng이 자리 잡으면 startflow를 안내만 남길지 정한다.
- 새 프로젝트의 로그인은 직접 만든다(소셜 아님, 결제 없음) — `/기획`의 첫 시험 대상. 프로젝트 이름·레포는 아직 모름.

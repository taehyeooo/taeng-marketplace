# spec 대비 구현 점검 (보고만)

기계가 셀 수 있는 것(테스트가 요구사항을 인용하나)은 CI `check_docs.py`가, 판단이 필요한 것(구현이 요구사항대로인가)은 이 스킬이 본다(ADR 0014). 이 세션의 모델이 코드를 읽는다 — 유료 API는 쓰지 않는다(ADR 0002). 찾은 것을 자동으로 고쳐 쓰는 반복은 하지 않는다.

## 1. spec 고르기
- 사용자가 말한 spec, 없으면 지금 브랜치의 plan(`docs/plans/`에서 `issue`가 브랜치 이슈 번호인 것)의 `based_on`, 그것도 없으면 PR 본문의 링크. 모르겠으면 후보를 보여 주고 묻는다.
- spec에 `- **R-n** ...` ID가 없으면 멈추고 알린다 — 이 스킬은 ID 있는 spec만 본다(필요하면 spec에 ID를 붙이는 것부터, `/intaeng:기획` 6단계).

## 2. 연결된 테스트 모으기
```bash
python scripts/check_docs.py      # "요구사항 → 테스트 연결" 줄: spec별 연결 수·빠진 ID
git grep -n "<slug>#R-"           # ID별 테스트 위치 (slug = spec 파일 이름에서 날짜·.md 뺀 것)
```

## 3. ID마다 판단
각 R-ID 문장을 조건·대상·동작으로 나누고, 관련 코드와 테스트를 **직접 읽는다**(plan 단계의 "확인:" 줄, 테스트 위치, 코드 검색). 추측으로 채우지 않는다.

| 판단 | 기준 |
|---|---|
| 구현 | 문장의 모든 조건·동작을 코드에서 찾았고, 그 동작을 확인하는 테스트·명령이 있다 |
| 부분 구현 | 일부 조건·동작만 있거나, 코드는 있는데 확인(테스트·명령·화면)이 없다 |
| 미구현 | 코드에서 찾지 못했다 |
| 확인 못 함 | 화면·외부 서비스·CI 설정처럼 이 세션에서 볼 수 없다 — 숨기지 않고 따로 센다 |

- 증거는 `파일:줄`로(코드와 테스트 각각). 테스트가 있어도 요구사항을 실제로 단언하지 않으면 "부분 구현"이다.
- 문서·설정 요구사항(템플릿·README·CI 작업)은 그 파일의 줄이 증거다.

## 4. 보고 (PR 본문에 그대로)
```
spec: docs/specs/<파일> v<번호> — 구현 a / 부분 b / 미구현 c / 확인 못 함 d, 일치율 = (a + 0.5×b) / (a+b+c) = NN%

| ID | 요구사항(짧게) | 판단 | 코드 | 테스트 |
|---|---|---|---|---|
| R-1 | ... | 구현 | `src/x.py:120` | `tests/test_x.py:88` |

빠진 것: R-4 — <무엇이 없나, 어디에 넣을 법한가>
```
- 일치율 공식은 위 하나만 쓴다(확인 못 함은 분모에서 뺀다). CI 연결률(테스트 인용 비율)과 다른 숫자임을 같이 적는다.
- `intaeng:wrap-up` 4번의 확인 증거 표는 이 표를 쓴다(이 PR이 다룬 ID만 남겨도 된다).

## 5. 하지 않을 것
- 코드·테스트·spec을 고치지 않는다. 빠진 것을 고칠지, spec을 바꿀지(새 번호·version 올림)는 사람이 정한다 — 물어본 뒤에 한다.
- 숫자를 채우려고 테스트에 `<slug>#R-n`을 붙이지 않는다. 정말 그 요구사항을 확인하는 테스트에만.

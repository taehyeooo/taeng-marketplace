# 기능명세서 (intaeng /기획)

사용자의 자연어 아이디어를 개발에 바로 쓸 수 있는 기능명세서로 만든다.
목표는 **코딩 전에 애매한 결정을 전부 끝내 두는 것**이다. 구현 중 AI가 임의로 정책을 정하지 않도록, 결정이 필요한 지점은 모두 사용자에게 묻고 문서에 기록한다. "내가 없어도 개발"은 개발 도중 사람을 찾지 않는다는 뜻이다 — 결정은 시작 전에 한 번.

## 진행 원칙
- **지식베이스 먼저**: 묻기 전에 `knowledge-base/decisions/`(ADR)와 `docs/specs/`의 지난 "결정 사항"을 찾는다. 이미 정한 정책이면 묻지 않고 그대로 쓰고 "결정 사항"에 근거(ADR 번호·spec)를 적는다. 비용 0원·샘플 먼저 같은 기본 원칙도 묻지 않는다.
- 정책·규칙이 애매하면 임의로 정하지 말고 **객관식**으로 묻는다.
  - AskUserQuestion 도구가 있으면 그것을, 없으면 텍스트로.
  - 질문 하나당 선택지 3~4개, 추천안에는 "(추천)", "직접 입력"도 허용.
  - 한 번에 최대 4개. 많으면 기능 단위로 나눠 묻는다.
- 사용자가 준 아이디어 범위를 벗어나는 기능은 추가하지 않고 **"추가 제안"**으로만 분리해 보여 준다.
- 사용자가 답한 결정은 모두 문서의 **"결정 사항"**에 누적 기록한다.

## 두 방식
- **같이 하기(기본)** — 사용자가 있을 때. 아래 단계를 순서대로, 각 단계가 끝나면 멈추고 확인받는다.
- **맡기기(자율 모드)** — "나 없이 진행해", "자고 일어나서 볼게"처럼 맡기고 자리를 비울 때(ADR(자율 모드)). 0단계에서 기능 묶음별 정책 질문을 **한 번에 모아** 묻는다. 답이 없는 것은 "(추천)"으로 정해 "결정 사항"에 `가정 n — 추천안, 이유`로 적고 멈추지 않고 6단계까지 간다. 끝에 가정 목록을 한 번에 확인받는다.

## 단계

### 0. 아이디어 받기
아이디어가 충분하지 않으면 짧게 묻는다(이미 주어졌으면 바로 1단계):
- 어떤 앱인지, 핵심 기능 2~5개, 주요 사용자, 플랫폼(iOS/Android/웹), 기술 스택 선호
- **완료 기준을 무엇으로 재나**(테스트·화면·건수 — "빠르다"면 몇 초를 무엇으로)
- **사람 손이 필요한 일**(DB 프로젝트, 키·비밀값, 외부 가입·콘솔 설정, 도메인) — 지금 목록으로 알려 주고, 사람이 하는 동안 할 수 있는 일을 같이 적는다. 비밀값은 채팅에 붙여넣지 않게 한다.
- 화면이 있으면 **레퍼런스** 1~3개(좋아하는 앱·화면)
- 기술 스택의 **무료 한도**를 확인해 적는다(ADR(비용 0원))

### 1. PRD 초안
개요(한 문단) · 문제와 해결 방안 · 타깃 사용자와 주요 사용 시나리오(3~5개) · 성공 지표와 위험 요소 · 범위(이번 버전 포함 / 제외) → 멈추고 확인.

### 2. 기능 트리
- 대기능 > 세부 기능 계층, 번호(예: 1. 커플 기념일 관리 > 1.1 커플 디데이 확인). Mermaid mindmap으로도.
- 아이디어에는 없지만 필요한 기반 기능(회원가입·로그인, 온보딩, 알림 설정, 계정 삭제 등)은 **"필수 기반 기능"**으로 따로 표시해 포함 여부를 묻는다.

→ 멈추고 확인.

### 3. 기능별 상세
세부 기능마다:
- 설명 · 권한·접근(누가 보고·만들고·수정·삭제) · 비즈니스 규칙(조건·제한·알림 시점) · 데이터(항목·필수값·관계·유일성·삭제·보관) · 화면(관련 화면과 빈·로딩·오류 상태) · 예외 상황(네트워크·권한 없음·연결 해제)
- **확인 방법**: 이 기능이 끝났다고 무엇으로 확인하나(테스트·화면·건수) 한 줄

애매한 부분은 객관식 질문으로 모아서 묻는다. 예: 상대방 알림은 언제 보낼까요?(추가 즉시 / 하루 묶음 / 알림 설정 따름 / 직접 입력), 완료된 항목은 언제까지 남길까요?(계속 보관 / 1년 후 삭제 / 30일 후 삭제)

→ 답 반영 후 멈추고 확인.

### 4. 데이터 모델
기능별 데이터를 합쳐 엔티티(테이블)·필드·타입·관계(1:N 등)·제약조건. Mermaid erDiagram. 접근 제어가 중요하면 행 단위 권한 규칙(예: Supabase RLS). → 멈추고 확인.

### 5. 자체 점검
아래로 빠진 것을 찾아 보완점을 보고하고, 필요한 질문을 더 한다.
- 모든 기능에 권한·데이터·예외·확인 방법이 있는가
- 삭제·탈퇴·연결 해제 때 데이터 처리 규칙
- 알림 시점과 조건
- 시간대·날짜 기준
- 중복·동시 수정 처리
- 개인정보·접근 제어
- 앱 이름, 번들 ID 같은 기본 정보
- 사람 손이 필요한 일이 모두 목록에 있는가

### 6. 확정 → spec
사용자가 "확정"이라고 하면(맡기기면 5단계 뒤 바로) [template.md](template.md)로 `docs/specs/YYYY-MM-DD-<이름>.md`에 저장한다(경로를 지정하면 그 경로).
- 4장 세부 기능마다 요구사항 ID: `- **R-1** 1.1 <세부 기능명> — <한 줄>`. 상세는 그 아래.
- 여러 기능에 걸친 큰 정책(탈퇴 데이터 보관 기간 등)은 ADR로도 남길지 묻는다(`docs/templates/adr.md`, 목록 `knowledge-base/decisions/README.md`).

### 7. plan
`docs/templates/plan.md`로 `docs/plans/YYYY-MM-DD-<이름>.md` — `based_on: docs/specs/<파일> v1`, 체크 단계 줄 끝에 `(R-n)` 인용, 기반 기능·데이터 모델 먼저. `python scripts/check_docs.py`가 통과해야 한다. now.md "다음 할 일"에 plan 첫 단계를 적는다.

## 끝나면 보고
만든 문서(spec·plan·ADR), 결정 사항 수(지식베이스에서 가져온 것 / 새로 물은 것 / 가정), 사람 손이 필요한 일 목록, 미결 사항.

# 새 작업 시작하기

작업 하나 = 이슈 하나 = 브랜치 하나 = 워크트리 하나(`CLAUDE.md` "워크트리 흐름"·"Git 컨벤션").

## 1. 브랜치 확인
- `git branch --show-current`. 기본 브랜치(`main`)의 메인 체크아웃이면 여기서 일하지 않고 워크트리를 만든다. 이미 작업 브랜치인데 이름이 `타입/#이슈번호-내용`이 아니면 이슈를 만들고 `git branch -m <새 이름>`.
- 타입은 커밋 타입과 같다(`feat`·`fix`·`docs`·`style`·`refactor`·`chore`·`perf`·`test`).

## 2. 이슈 → 브랜치 → 워크트리
```bash
gh issue create --title "feat: <내용>" --body "<무엇을 왜, 한두 줄>"    # 번호 확인
git fetch origin
git worktree add ../<레포 이름>-<slug> -b feat/#<번호>-<slug> origin/main
```
- 경로는 메인 체크아웃 옆(`../<레포 이름>-<slug>`). 도구가 워크트리를 이미 만들어 줬으면 브랜치 이름만 확인한다.
- 이후 명령은 **그 워크트리 폴더에서**. 훅이 꺼져 있으면 `git config core.hooksPath .githooks`(ADR(커밋 규칙)).
- 다른 작업이 같은 파일을 고치는 중이면(now.md "진행 중", `git worktree list`) 겹치는 파일과 ADR 번호를 먼저 정한다.

## 3. 맥락 읽기
- `knowledge-base/now.md`(진행 중인 일과 겹치나), `knowledge-base/index.md`, `knowledge-base/decisions/README.md`(ADR 목록)에서 관련 ADR 본문.
- 고칠 경로의 `.claude/rules/*.md`(목록은 CLAUDE.md "경로별 규칙").
- **ADR과 부딪히면** 하기 전에 "ADR 00xx는 …인데 이번 일은 …라 부딪혀요. 결정을 바꿀까요, 이번 일을 맞출까요?"로 묻는다.

## 4. 무엇을 만드나 — 갈래 나누기
모르는 칸을 채워 넣지 않는다. 일의 크기에 따라 넘길 곳이 다르다.

| 일 | 할 것 |
|---|---|
| 작은 일(문서 한 줄, 오타, 작은 버그) | **완료 기준**("끝났다"를 무엇으로 확인하나 — 테스트·화면·건수)과 **범위 밖**(이번에 하지 않을 것)만 한 메시지로 묻고 바로 진행 |
| 새 기능·새 프로젝트 | `/intaeng:기획`(`intaeng:feature-spec`)으로 넘긴다 — 모호함 질문, 사람 손이 필요한 일, spec(요구사항 ID)·plan은 거기서 만든다. 사용자가 쓰는 큰 기능이면 `docs/templates/interview.md`(퀄리티 기준서 인터뷰)를 먼저 해서 답을 spec `## 퀄리티 기준서`에 둔다 |
| 화면을 새로 만들거나 구조를 바꾸는 일 | 기획이 끝난 뒤 `/intaeng:디자인`(`intaeng:design-flow`) — 구조 시안 3개 → 세부 시안 → 적용 → 고도화. 작은 화면 수정(문구·간격 하나)은 3↔4단계만. 점검은 `intaeng:design-review`, 문구는 `intaeng:ux-writing-ko` |

- **사람 손이 필요한 일**(DB 프로젝트, 키·비밀값, 외부 콘솔 가입·설정, 도메인)은 중간에 하나씩 멈춰 묻지 않는다 — 시작할 때 목록으로 한 번에 알려 주고, 사람이 하는 동안 할 수 있는 일(문서·테스트·화면 초안)을 같이 적는다. 비밀값은 채팅에 붙여넣지 않게 한다.
- 비용 0원·무료 티어 한도(ADR(비용 0원)), 내 데이터 20~30개로 먼저 검증(ADR(샘플 먼저))은 묻지 않고 지킨다.

## 5. 시작 표시
- now.md "진행 중"에 이 작업 한 줄(이슈·브랜치·워크트리).
- 구현은 plan 순서대로, 테스트 먼저 → 구현. 테스트·빌드 명령은 레포의 것(CLAUDE.md나 README에 적힌 것)을 쓴다. 끝나면 `intaeng:wrap-up`.

## 6. 자율 모드 — 맡기고 자리를 비울 때
사용자가 "나 없이 진행해", "아침에 볼게", "맡길게"라고 하면 이 갈래로 간다(ADR(자율 모드)). **묻는 것은 시작할 때 한 번뿐이다.** 1~3번은 같다.
1. **한 번에 묻기**: 범위(작은 일이면 완료 기준·범위 밖, 새 기능·새 프로젝트면 `/intaeng:기획`의 맡기기 방식 — 정책 질문을 처음에 모아 한 번에. 큰 기능이면 퀄리티 기준서 인터뷰를 먼저 — 맡기고 자리를 비우면 고칠 기회가 없으니 기준을 먼저 받는다) + 사람 손이 필요한 일 + **권한 묶음**을 한 메시지로. 권한 묶음은 기본안을 보여 주고 고칠 것만 받는다:
   ```
   권한 묶음 (#<이슈> 이 작업에만)
   - 머지: CI 모두 통과·커밋과 PR 본문에 서명·트레일러 없음을 확인한 뒤 Claude가 squash 머지
   - 묻기(승인 대기로): 공통 모듈 변경(<경로>), ADR 새로 쓰기·고치기, 기존 ADR과 부딪힘, 유료 API·플랜,
     외부 가입·콘솔 설정·비밀값, 데이터·원격 브랜치 지우기, 범위 밖 일
   - 멈춤: 같은 실패 3번, 사용량 한도 → now.md에 어디까지 했는지 남기고 멈춤
   - 끝: 아침 보고(머지됨·승인 대기·막힘·기록 링크)
   - 사용량 여유(선택): /usage로 본 남은 양·리셋 시각 — 적으면 PR 수를 줄이거나 쪼갠다
   ```
   Claude는 남은 사용량을 볼 수 없다 — 사용자가 알려 준 만큼만 계획에 쓰고, 모르면 아래 "한도에 대비"대로 간다.
2. **기록**: 받은 답을 그대로 spec `## 자율 모드 권한`에 날짜와 함께 적고, now.md "진행 중" 이 작업 줄에 `자율 모드 — 권한: <spec 경로>`. 새 세션(`intaeng:resume`)·하위 에이전트(`intaeng:delegate-pr`)는 대화 기억이 아니라 여기서 권한을 읽는다.
3. **실험 기록**: PR이 둘 이상이면 `docs/templates/rehearsal.md` 양식으로 실험 기록을 만든다(예: `knowledge-base/rehearsals/YYYY-MM-DD-<slug>.md` — 새 폴더면 README를 두고 `knowledge-base/index.md`에 한 줄, 없으면 문서 검사 실패). 막힌 곳·결정이 필요했던 순간은 그때그때 한 줄씩.
4. **그 뒤로는 묻지 않는다**: 답이 없는 칸·세부 결정은 spec "열린 질문 / 가정"에 `가정 n — …`으로 쓰고 진행한다. "spec 확정"은 PR 리뷰로 대신한다(가정에 적는다).
5. **사용량 한도에 대비**(한도는 예고 없이 끊겨 그때는 기록할 틈이 없다):
   - **PR은 작게**: plan 단계 하나가 한 시간을 넘을 것 같으면(서버 + 화면, 화면 두 덩이) a·b로 나눈다.
   - **위치는 미리**: PR마다 `intaeng:wrap-up`이 쓰는 now.md(머지 뒤 상태)에 "<n>까지 머지, 다음 <n+1> — plan 단계 번호"를 적는다. 끊기면 새 세션 `intaeng:resume`이 이걸로 이어받고, 머지된 PR은 다시 하지 않는다.
   - 하위 에이전트(`intaeng:delegate-pr`)를 한 세션에서 연달아 많이 돌리면 한도가 빨리 찬다 — 기대는 것은 순서대로 하나씩, 병렬은 서로 기대지 않는 둘까지.
6. **권한 밖이면 멈추지 않고 비켜 간다**: now.md `## 승인 대기`에 한 줄(무엇 — 왜 권한 밖 — 대신 한 것 — PR·브랜치), 실험 기록 표에 "사람이 필요했나: 승인 대기". 그 단계는 PR을 올리되 머지하지 않고, 기대지 않는 다음 단계를 계속한다. 모든 단계가 막히면 멈춘다.
7. 끝나거나 멈추면 `intaeng:merge-train` 5번 **아침 보고**.

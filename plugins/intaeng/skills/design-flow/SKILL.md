# 디자인 4단계 (intaeng /디자인)

**큰 것 → 작은 것**: 구조(배치·화면 구성·핵심 흐름)를 고르기 전에 글꼴·색을 고르지 않는다. 사용자는 단계마다 **고르기만** 하고, 고른 시안이 곧 실제 앱이다.
작은 수정(문구 한 줄, 간격 하나)은 1·2단계 없이 3↔4만 한다.

## 시작 전
- **지식베이스 먼저**: `docs/specs/`의 기능명세서(화면 목록·레퍼런스), `knowledge-base/decisions/`의 디자인 결정(브랜드·글꼴·터치 크기 등)을 읽는다. 정해진 것은 다시 묻지 않는다.
- 명세서가 없으면 화면 목록과 레퍼런스(좋아하는 앱·화면 1~3개)를 짧게 묻는다. 기획부터 필요하면 `/intaeng:기획`을 권한다.
- 쓸 디자인 스킬이 설치돼 있는지 본다(아래 "스킬"). 없으면 설치를 권하고, 없는 채로 할 때는 그 스킬 몫을 이 문서 기준으로 대신한다고 말한다.

## 두 방식
- **같이 하기(기본)**: 1·2단계 끝에 사용자가 고르고, 3단계 뒤 써 보고 의견 → 4단계. 고르는 질문은 객관식(선택지 3~4개, "(추천)").
- **맡기기(자율 모드)**: 1·2단계에서 추천안을 고르고 이유를 적은 뒤 끝까지 간다. 고르지 않은 시안도 지우지 않고 남겨, 돌아온 사용자가 나란히 보고 바꿀 수 있게 한다. 끝에 "고른 것·이유·바꾸는 법"을 보고한다.

## 1. 구조 시안 3개
- 레퍼런스에서 출발해 **배치·화면 구성·핵심 흐름이 서로 다른** 시안 3개(예: 목록형 / 카드형 / 시간표형). 글꼴·색은 기본값 그대로.
- `ui-ux-pro-max`로 그 화면 종류의 패턴·UX 가이드라인을 찾고, `frontend-design`으로 방향을 잡는다. 시안마다 "무엇이 다른가, 누구에게 맞나" 한 줄.
- **아티팩트로 그리지 않는다**(토큰이 많이 들고, 고른 뒤 다시 옮겨 그려야 한다). 실제 앱 안 변형으로 만든다: 쿼리 `?ux=a|b|c`로 구조를 바꾸고, **개발 서버에서만** 켜지게 한다(운영 빌드에 시안 코드가 들어가지 않게 — 빌드 결과에서 확인).
- 나란히 보기: `${CLAUDE_PLUGIN_ROOT}/skills/design-flow/compare.html`을 브라우저로 열고(주소에 `?base=http://localhost:3000/&v=ux=a&v=ux=b&v=ux=c&w=390`처럼 값을 넣어 열 수도 있다) 개발 서버 주소와 시안 목록(`?ux=a`, `?ux=b`, `?ux=c`)을 넣으면 휴대폰·데스크톱 폭으로 나란히 띄워 칸 안에서 눌러 볼 수 있다. 같은 폭·모드로 스크린숏을 찍어(레포에는 넣지 않음) 보고에 붙인다.
- → 사용자가 하나 고름. 고른 것과 이유를 명세서 "결정 사항"에 적는다.

## 2. 세부 시안
고른 구조 위에서 두 가지를 보인다.
- **느낌 — 토큰 세트 2~3개**: 글꼴·색·간격·모서리·밀도. 값은 CSS 변수(앱은 테마 객체) 묶음으로 두고 `?variant=` 로 바꾼다. 색은 역할 이름(배경·면·글자·강조·위험)으로, 본문 대비 4.5:1 이상. `ui-ux-pro-max`(팔레트·글꼴 조합).
- **UX 디테일**: 움직임(들어올 때·완료 피드백), 입력 방식, 빈·불러오는 중·오류 상태. `emil-design-eng`(움직임·디테일), 문구는 `intaeng:ux-writing-ko`.
- 같은 나란히 보기로 보인다. → 사용자가 조합을 고름(예: 느낌 B + 완료 움직임 2). 결정 사항에 적는다.

## 3. 적용
- 고른 조합을 기본 화면으로 만들고 시안 장치(`?ux=`·`?variant=`)는 개발용으로만 남기거나 지운다.
- 지킬 것: 색·간격·글자는 토큰 이름으로만(숫자·`#hex` 직접 쓰지 않기), 데이터 화면은 내용·빈·불러오는 중·오류 네 상태, 누르는 것 44×44px 이상, 밝은·어두운 모드, 390·768·1280px에서 가로 스크롤 없음, 한글은 `word-break: keep-all`.
- `intaeng:design-review`로 점검하고 고친다. 레포에 화면 자동 검수·토큰 검사가 있으면 돌린다.
- → 사용자가 써 보고 의견(말로, 또는 화면 요소를 가리켜서).

## 4. 고도화 (3↔4 반복)
- 의견 하나하나를 스킬 규칙에 대응시켜 고친다. 대응되는 규칙이 없으면 "규칙 없음 — 사용자 취향"으로 적고 그대로 반영한다.
- 전·후 스크린숏(같은 폭·모드)과 표:

| 사용자 의견 | 대응한 스킬 규칙 | 바뀐 것 | 전·후 |
|---|---|---|---|
| 예: "너무 심플해" | `frontend-design` — 흔한 기본값 피하기, 위계 | 제목 단계·강조색 면적 | `before-390.png` / `after-390.png` |

## 화면 PR 본문 — 스킬 적용 표
그 단계에서 쓴 스킬을 모두 적는다. 읽었지만 바꿀 것이 없었으면 "없음"과 이유.

| 스킬 | 읽은 규칙 | 이 PR에서 바뀐 것 | 적용 안 한 것과 이유 |
|---|---|---|---|

1·2단계면 나란히 보기 스크린숏(또는 보는 법)과 사용자가 고른 것, 4단계면 위 "의견 → 규칙 → 바뀐 것" 표.
